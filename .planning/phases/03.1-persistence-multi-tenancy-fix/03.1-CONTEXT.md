# Phase 03.1: Persistence Multi-Tenancy Fix - Context

**Gathered:** 2026-03-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Fix cross-phase integration gaps — SaveCampaign preserves tenant ownership during agent turns and Web API auto-creates database on first launch. Three confirmed gaps: (1) CampaignPlugin calls parameterless SaveCampaign at 4 sites, losing UserId; (2) Program.cs has no Database.Migrate(), so fresh launch fails; (3) GameSessionService doesn't pass UserId context to plugins.

</domain>

<decisions>
## Implementation Decisions

### Tenant context propagation
- Create a scoped `ITenantContext` service with a `UserId` property
- Interface lives in `WretchedWhispers.Core` alongside other interfaces; implementation in Infrastructure
- Accessing `UserId` before it's set throws `InvalidOperationException` (fail-fast — catches misconfiguration immediately)
- Set `UserId` at the endpoint level (middleware or endpoint filter) from JWT claims
- Plugins resolve `ITenantContext` via constructor DI — no coupling to HTTP layer
- Console apps set a "system" or "console" user ID via `ITenantContext` at startup for consistency

### Database initialization
- Call `Database.MigrateAsync()` in `Program.cs` before `app.Run()` — same pattern as console apps
- Log an `ILogger` info message when migration/creation occurs (e.g., "Database migrated successfully")
- SQLite + single-instance deployment makes auto-migrate safe

### SaveCampaign API design
- Parameterless `SaveCampaign(campaign)` internally reads `ITenantContext.UserId` — all save paths automatically preserve tenant
- Explicit `SaveCampaign(campaign, userId)` overload stays for tests and seeding where no HTTP/tenant context exists
- Update `ICampaignsRepository` interface to reflect the new design — all implementations follow the same tenant-aware pattern
- Only Campaigns get tenant-awareness — Characters and Encounters are accessed through Campaign (aggregate root with UserId FK), so tenant isolation at Campaign level is sufficient

### Fix scope
- Targeted fix for the 3 specific gaps — don't touch code that isn't broken
- Add integration tests that verify UserId survives a full agent turn (end-to-end through GameSessionService)
- Update console apps to use `ITenantContext` for consistency across all code paths

### Claude's Discretion
- ITenantContext implementation details (class name, namespace organization)
- Middleware vs endpoint filter for setting tenant context
- Exact test structure and assertions for integration tests
- Console app user ID value ("system", "console-user", etc.)
- Whether to log at Info or Debug level for migration messages

</decisions>

<specifics>
## Specific Ideas

- Existing `CampaignMultiTenancyTests` verify the repository overload works — new tests should verify the full GameSessionService -> CampaignPlugin -> Repository flow preserves tenant
- Console apps already call `db.Database.Migrate()` explicitly — API should follow the same pattern
- The existing `ImportPluginFromObject` pattern for Scoped plugin resolution in GameSessionService is the right place to inject ITenantContext
- Phase 3 STATE.md decisions apply: "Plugins registered as Scoped and resolved via ImportPluginFromObject for request-scoped DbContext alignment"

</specifics>

### Reusable Assets
- `SqliteCampaignsRepository.SaveCampaign(campaign, userId)`: Already correctly preserves UserId — parameterless overload just needs to call this with ITenantContext.UserId
- `CampaignEntity.UserId` with required max-length constraint and index: Schema already supports multi-tenancy
- `CampaignMultiTenancyTests`: Existing test patterns for tenant isolation verification
- Console app migration pattern (`db.Database.Migrate()`): Proven pattern to replicate in API

### Established Patterns
- Scoped DI for web API services (`AddDomainServices`): ITenantContext fits naturally as Scoped
- Primary constructors for services: ITenantContext injection follows existing pattern
- `ImportPluginFromObject` for request-scoped plugin resolution: Plugin instances already get fresh DI per request

### Integration Points
- `CampaignPlugin` (4 SaveCampaign call sites): Primary fix location — will auto-resolve via repository's ITenantContext
- `GameSessionService.ExecuteAgentTurnAsync`: Plugin construction already uses DI scope — ITenantContext will be available
- `SessionEndpoints`: Already extracts UserId from claims — needs to set ITenantContext before calling service
- `Program.cs` app startup: Migration call goes between `builder.Build()` and `app.UseAuthentication()`

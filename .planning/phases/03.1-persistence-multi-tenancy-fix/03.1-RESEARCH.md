# Phase 03.1: Persistence Multi-Tenancy Fix - Research

**Researched:** 2026-03-03
**Domain:** EF Core multi-tenancy, ambient context pattern, ASP.NET Core scoped services
**Confidence:** HIGH

## Summary

This phase fixes three confirmed integration gaps where tenant ownership (UserId) is lost during agent turns. The root cause is clear: `CampaignPlugin` and `CampaignService` call the parameterless `SaveCampaign(campaign)` overload which writes `UserId = ""` (empty string), stripping ownership from campaigns modified during Semantic Kernel agent turns. The API endpoint `CreateSession` correctly uses `SaveCampaign(campaign, userId)` but all downstream saves through plugins and services lose that association.

The fix is architectural but small-scoped: introduce a scoped `ITenantContext` that carries UserId through the DI scope, make the parameterless `SaveCampaign` read from it, and add `Database.MigrateAsync()` to the API startup. The existing DI architecture (Scoped plugins resolved via `ImportPluginFromObject`, Scoped DbContext, Scoped repositories) already provides the correct scope boundary -- ITenantContext just needs to ride the same scope.

**Primary recommendation:** Create `ITenantContext` interface in Core, implement in Infrastructure, register as Scoped, set from endpoint code, and have `SqliteCampaignsRepository` read it in the parameterless `SaveCampaign`. This preserves all existing signatures while making every save path tenant-aware by default.

### Pattern 1: Scoped Ambient Tenant Context
**What:** A Scoped service that carries the current user's identity through the entire DI scope. Set once at the request boundary, consumed by any service in the same scope.
**When to use:** When multiple downstream services need tenant identity but should not receive it as a parameter (separation of cross-cutting concerns from business logic).
**Example:**
```csharp
// Core/ITenantContext.cs
namespace WretchedWhispers.Core;

public interface ITenantContext
{
    string UserId { get; }
    void SetUserId(string userId);
}

// Infrastructure/TenantContext.cs
namespace WretchedWhispers.Infrastructure;

public sealed class TenantContext : ITenantContext
{
    private string? _userId;

    public string UserId => _userId
        ?? throw new InvalidOperationException(
            "UserId has not been set. Ensure ITenantContext is configured before accessing UserId.");

    public void SetUserId(string userId)
    {
        ArgumentException.ThrowIfNullOrEmpty(userId);
        _userId = userId;
    }
}
```

### Pattern 2: Repository with Tenant Context Injection
**What:** The repository constructor receives ITenantContext and uses it as the default source of UserId for saves. The explicit userId overload remains for test/seed scenarios.
**When to use:** When the same repository method is called from both HTTP-scoped and non-HTTP contexts.
**Example:**
```csharp
// Updated SqliteCampaignsRepository
public class SqliteCampaignsRepository(
    WretchedWhispersDbContext db,
    JsonSerializerOptions jsonOptions,
    ITenantContext tenantContext) : ICampaignsRepository
{
    public async Task SaveCampaign(Campaign campaign)
    {
        // Delegates to the userId overload using ambient tenant context
        await SaveCampaign(campaign, tenantContext.UserId);
    }

    public async Task SaveCampaign(Campaign campaign, string userId)
    {
        // Existing implementation unchanged
    }
}
```

### Pattern 3: Endpoint Filter for Tenant Setup
**What:** An endpoint filter that extracts UserId from JWT claims and sets it on ITenantContext before the endpoint handler runs.
**When to use:** When all endpoints in a group need the same pre-processing.
**Example:**
```csharp
// Option A: Inline in SessionEndpoints (simpler, follows existing pattern)
group.AddEndpointFilter(async (context, next) =>
{
    var http = context.HttpContext;
    var userId = http.User.FindFirstValue(ClaimTypes.NameIdentifier);
    if (string.IsNullOrEmpty(userId))
        return Results.Unauthorized();

    var tenantContext = http.RequestServices.GetRequiredService<ITenantContext>();
    tenantContext.SetUserId(userId);
    return await next(context);
});

// Option B: Middleware (broader scope, runs for all requests)
app.Use(async (context, next) =>
{
    var userId = context.User.FindFirstValue(ClaimTypes.NameIdentifier);
    if (!string.IsNullOrEmpty(userId))
    {
        var tenantContext = context.RequestServices.GetRequiredService<ITenantContext>();
        tenantContext.SetUserId(userId);
    }
    await next();
});
```

**Recommendation:** Use an endpoint filter on the `/sessions` group. It is more targeted (only runs for session endpoints that need it), and it follows the existing pattern where each endpoint already extracts `userId` from claims. The filter centralizes this extraction and eliminates the repeated `FindFirstValue` + null check boilerplate in each handler.

### Pattern 4: Database Migration at Startup
**What:** Call `MigrateAsync` during app startup to ensure schema exists.
**When to use:** Single-instance SQLite deployments where there is no risk of concurrent migrations.
**Example:**
```csharp
// In Program.cs, between builder.Build() and app.UseAuthentication()
var app = builder.Build();

// Auto-create/migrate database on first launch
using (var scope = app.Services.CreateScope())
{
    var db = scope.ServiceProvider.GetRequiredService<WretchedWhispersDbContext>();
    await db.Database.MigrateAsync();
    var logger = scope.ServiceProvider.GetRequiredService<ILogger<Program>>();
    logger.LogInformation("Database migrated successfully");
}

app.UseAuthentication();
```

### Anti-Patterns to Avoid
- **Passing userId as parameter through every method call:** This is what the current broken design partially does. The whole point of ITenantContext is to avoid threading userId through CampaignPlugin -> CampaignService -> Repository manually.
- **Using HttpContext.Current or IHttpContextAccessor in domain/infrastructure layer:** Couples infrastructure to HTTP. ITenantContext is the abstraction that keeps layers clean.
- **Making ITenantContext a Singleton or Transient:** Singleton would share state across requests (catastrophic data leak). Transient would create separate instances per resolution (each service gets its own empty context). Must be Scoped.
- **Forgetting to set ITenantContext in console apps:** Would cause InvalidOperationException on first SaveCampaign. Console apps must explicitly set a system user ID.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Database schema management | Custom SQL scripts or EnsureCreated | `Database.MigrateAsync()` | Applies migrations incrementally; EnsureCreated cannot update existing databases |
| Request-scoped user context | Manual parameter threading | Scoped DI + ITenantContext | DI scope already exists and is the correct boundary; parameters create coupling |
| JWT claim extraction | Custom token parsing | `ClaimTypes.NameIdentifier` from `HttpContext.User` | Identity middleware already parses and validates the token |

## Common Pitfalls

### Pitfall 1: ITenantContext Not Set Before Repository Access
**What goes wrong:** `InvalidOperationException` thrown when repository tries to read `UserId` from an uninitialized `TenantContext`.
**Why it happens:** A code path reaches `SaveCampaign(campaign)` without an endpoint filter or console setup having called `SetUserId`.
**How to avoid:** (a) Endpoint filter on the session group guarantees it is set for all web requests. (b) Console apps set it at startup. (c) The fail-fast exception makes this immediately visible.
**Warning signs:** `InvalidOperationException: UserId has not been set` in logs.

### Pitfall 2: CampaignService Also Calls Parameterless SaveCampaign
**What goes wrong:** The CONTEXT.md mentions 4 call sites in CampaignPlugin, but `CampaignService` has 6 additional parameterless `SaveCampaign` calls (lines 15, 28, 36, 44, 61, 84). If only the plugin is considered fixed, the service calls still strip UserId.
**Why it happens:** CampaignService.AdvanceTime and CampaignService.AdvanceTimeWithRest are called by CampaignPlugin.AdvanceTime and CampaignPlugin.Rest, which pass through to the service. The service calls `campaignsRepository.SaveCampaign(campaign)` -- the parameterless overload.
**How to avoid:** The ITenantContext-based fix in `SqliteCampaignsRepository` automatically fixes ALL parameterless callers (plugin, service, and any future code) without touching them. This is the beauty of the ambient context pattern.
**Warning signs:** If someone were to fix it by changing call signatures instead of the repository, they would need to update 10+ call sites and miss this.

### Pitfall 3: Scoped vs Transient Lifetime Mismatch
**What goes wrong:** If ITenantContext is registered with the wrong lifetime, it either shares state across requests (Singleton) or gets separate instances that are not pre-configured (Transient).
**Why it happens:** The console app infrastructure uses `AddSqliteInfrastructure` which registers everything as Transient. The web API uses `AddDomainServices` which registers everything as Scoped.
**How to avoid:** Register ITenantContext as Scoped in `AddDomainServices` and as Singleton in `AddSqliteInfrastructure` (console apps have one user for the entire process lifetime).
**Warning signs:** UserId is empty/null despite being set, or different repository instances see different tenant contexts.

### Pitfall 4: Program.cs Requires Async Main for MigrateAsync
**What goes wrong:** The current `Program.cs` is synchronous top-level statements. Calling `MigrateAsync()` requires `await`, which requires the method to be async.
**Why it happens:** Top-level C# programs support async automatically -- `await` in top-level statements makes the compiler generate an async entry point. But the call must be placed correctly between `builder.Build()` and `app.Run()`.
**How to avoid:** Simply use `await db.Database.MigrateAsync()` in the top-level statements. No special async configuration needed.
**Warning signs:** Compile error if you try to use `.Result` or `.Wait()` -- don't do that, use `await`.

### Pitfall 5: Existing Tests Mock ICampaignsRepository
**What goes wrong:** `CampaignServiceTests` uses `Mock<ICampaignsRepository>` and verifies `r.SaveCampaign(It.IsAny<Campaign>())`. Adding ITenantContext to the repository constructor does not break these tests because they mock the interface, not the implementation.
**Why it happens:** Moq creates a mock from the interface, not the concrete class. The mock's `SaveCampaign(Campaign)` still matches.
**How to avoid:** No action needed for mock-based tests. Only `SqliteTestBase`-derived tests that create `SqliteCampaignsRepository` directly need updating (pass a test ITenantContext).
**Warning signs:** `CampaignMultiTenancyTests` and `CampaignRoundTripTests` will fail to compile because `SqliteCampaignsRepository` constructor now requires `ITenantContext`.

### Pitfall 6: Console App Migration Pattern Difference
**What goes wrong:** Console apps use synchronous `db.Database.Migrate()`. The API should use async `db.Database.MigrateAsync()`. Don't copy-paste the console pattern verbatim.
**Why it happens:** Console apps use synchronous Semantic Kernel setup. The API already uses async throughout.
**How to avoid:** Use `MigrateAsync()` in the API. The console apps can stay synchronous.

### Complete ITenantContext Interface
```csharp
// WretchedWhispers.Core/ITenantContext.cs
namespace WretchedWhispers.Core;

/// <summary>
/// Provides ambient tenant context for the current operation scope.
/// Set at the request boundary (endpoint filter) or app startup (console).
/// </summary>
public interface ITenantContext
{
    /// <summary>
    /// The authenticated user's ID. Throws InvalidOperationException if not set.
    /// </summary>
    string UserId { get; }

    /// <summary>
    /// Sets the user ID for the current scope. Called once per request/operation.
    /// </summary>
    void SetUserId(string userId);
}
```

## Open Questions

1. **Endpoint filter vs per-handler setup**
   - What we know: Both approaches work. Endpoint filter centralizes the logic.
   - What's unclear: Whether the existing per-handler `userId` extraction should be completely removed or kept as a belt-and-suspenders check.
   - Recommendation: Use endpoint filter. Remove redundant `FindFirstValue` + null checks from individual handlers since the filter guarantees it. Keep the filter's Unauthorized return as the single auth gate.

2. **Console app ITenantContext lifetime**
   - What we know: Console apps register infrastructure as Transient. A Transient ITenantContext would lose state between resolutions.
   - What's unclear: Whether to change console registration to Singleton or to set ITenantContext on each resolved scope.
   - Recommendation: Register as Singleton in `AddSqliteInfrastructure` since console apps have a single user for the entire process lifetime. Set once at startup.

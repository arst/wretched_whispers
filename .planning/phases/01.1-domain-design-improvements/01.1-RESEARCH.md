# Phase 01.1: Domain Design Improvements - Research

**Researched:** 2026-03-03
**Domain:** C# DDD domain layer refactoring (WretchedWhispers.Core)
**Confidence:** HIGH

## Summary

This phase is a pure correctness and structural refactoring of the domain layer. No new capabilities are added. The codebase is a relatively small C# DDD project (~60 source files, ~458-line Character god class) using System.Text.Json for persistence, Semantic Kernel plugins as the integration layer, and xUnit/Moq for testing.

The work divides into four concerns: (1) fixing two critical bugs (inverted scroll restriction, public Encounter setters), (2) decomposing the Character god class and improving injury representation, (3) fixing aggregate boundary violations where the Semantic layer bypasses domain roots, and (4) mechanical sealing/cleanup. All changes must preserve JSON serialization round-trip compatibility (or update the serializer in lockstep) because persistence uses JSON blob storage.

**Primary recommendation:** Fix the two critical bugs first, then tackle Character decomposition and injury consolidation as the bulk of the work, fix aggregate boundaries, and finish with sealing/trivial cleanup. Every change must pass the existing serialization round-trip tests as the regression gate.

### Pattern 1: Move Armor Reduction to ArmorTier Strategy Objects
**What:** The `RollArmorReduction` method in Character.cs (lines 287-296) is a switch expression over ArmorTier subtypes. This logic belongs on the ArmorTier hierarchy itself -- each subtype already knows its DamageReduction DiceExpr.
**When to use:** When behavior varies by subtype and the subtype hierarchy already exists.
**Example:**
```csharp
// On ArmorTier base class:
public int RollDamageReduction(Dice dice)
{
    return DamageReduction.Sides == 0 ? 0 : dice.Roll(DamageReduction);
}

// In Character, replace switch with:
var armorReduction = Armor.Tier.RollDamageReduction(dice);
```
**Confidence:** HIGH -- The DamageReduction property already exists on each ArmorTier subtype; this is a mechanical move. The method can go directly on the abstract base class since all subtypes already define DamageReduction.

### Pattern 2: Injury Representation Consolidation
**What:** Replace 7 boolean injury flags (HasLostEye, HasStabbedLung, HasBrokenHand, HasCrushedFoot, HasSeveredArm, HasSmashedFace + IsDead from broken table) with a consolidated representation.
**When to use:** When multiple booleans represent variants of the same concept.

**Recommended approach: `[Flags] enum InjuryKind` + `InjurySet` value object**

```csharp
[Flags]
public enum InjuryKind
{
    None        = 0,
    LostEye     = 1 << 0,
    StabbedLung = 1 << 1,
    BrokenHand  = 1 << 2,
    CrushedFoot = 1 << 3,
    SeveredArm  = 1 << 4,
    SmashedFace = 1 << 5,
}

public readonly record struct InjurySet(InjuryKind Injuries)
{
    public bool Has(InjuryKind injury) => (Injuries & injury) == injury;
    public InjurySet Add(InjuryKind injury) => new(Injuries | injury);

    // Penalty calculation centralized here
    public int GetStrengthPenalty() => Has(InjuryKind.SeveredArm) ? 4
                                    : Has(InjuryKind.BrokenHand) ? 2 : 0;
    public int GetAgilityPenalty() => Has(InjuryKind.StabbedLung) || Has(InjuryKind.CrushedFoot) ? 2 : 0;
    // etc.
}
```

**Rationale for keeping IsDead separate:** IsDead is a terminal state that gates ALL further actions, not just a penalty modifier. It belongs at the Character level, not in the injury set. The `BrokenOutcome.Dead` still triggers `IsDead = true` on Character.

**Rationale for keeping IsInfected and IsDizzyFromMagic separate:** These are temporary conditions with their own lifecycle (infection is curable, dizzy resets at dawn). They are not injuries from the broken table. Keep them as separate booleans on Character.

**Confidence:** HIGH -- Flags enum is the natural C# representation for a fixed set of combinable states. Serializes as an integer, which is simpler than 7 booleans.

### Pattern 3: Character Decomposition via Extract Method Object
**What:** Extract large behavioral blocks from Character into focused helper types while keeping Character as the orchestrating aggregate root.
**When to use:** When a class has too many responsibilities but external callers need to go through one entry point.

**Recommended decomposition targets:**
1. **Combat resolution** (Attack, Defend, ReceiveDamage, CalculateDamageAfterDefense, ResolveDefence, ResolveBroken) -- Extract to a `CombatResolver` or inline methods that delegate to value objects
2. **Broken-state resolution** (ResolveBroken + the switch mapping BrokenOutcome to injury flags) -- Extract to a `BrokenResolver` static helper or method on InjurySet
3. **Challenge penalty calculation** (the switch blocks in Challenge that check injury flags) -- Move to InjurySet methods

**What stays on Character:** Public API methods (Attack, Defend, Challenge, Cast, Rest, BuyItem, Improve, Degrade), state mutation, and aggregate invariant enforcement.

**Confidence:** MEDIUM -- The exact decomposition boundary depends on how much the planner wants to move. The key constraint is preserving the public API surface.

### Pattern 4: Aggregate Boundary Enforcement
**What:** CharacterPlugin directly calls `character.Inventory.AddItem()`, `character.Inventory.RemoveItem()`, `character.Inventory.ConsumeItem()`, `character.Inventory.ReplenishItem()` -- bypassing the Character aggregate root.

**Recommended fix:** Add methods on Character that delegate to Inventory, then make Inventory's mutating methods internal (or route the plugin calls through Character).

```csharp
// On Character:
public void AddItem(InventoryItem item) { Inventory.AddItem(item); }
public void RemoveItem(Guid itemId) { Inventory.RemoveItem(itemId); }
public bool ConsumeItem(Guid itemId) { return Inventory.ConsumeItem(itemId); }
public void ReplenishItem(Guid itemId, int amount = 1) { Inventory.ReplenishItem(itemId, amount); }
```

Then update CharacterPlugin to call `character.AddItem(newItem)` instead of `character.Inventory.AddItem(newItem)`.

**Confidence:** HIGH -- Straightforward delegation pattern. The BuyItem method on Character already shows this pattern (it manipulates Inventory internally).

### Pattern 5: Inventory Record-to-Class Conversion
**What:** Inventory is declared as `public record Inventory(...)` with a mutable `List<InventoryItem>` parameter. This mixes value semantics (record) with reference semantics (mutable list). The `with` expression used in `Character.BuyItem()` and `Character.Improve()` creates a shallow copy, sharing the same list reference.

**Recommended fix:** Convert Inventory from `record` to `sealed class`. Update `Character.BuyItem()` and `Character.Improve()` to mutate in place instead of using `with` expressions.

```csharp
// Before (record with `with` expression):
Inventory = Inventory with { InventoryItems = Inventory.InventoryItems.Append(item).ToList() };

// After (sealed class, direct mutation):
Inventory.AddItem(item);
```

**Confidence:** HIGH -- BuyItem already validates preconditions, then can delegate to Inventory.AddItem directly.

### Anti-Patterns to Avoid
- **Breaking JSON serialization:** Every structural change must maintain round-trip compatibility. The JSON blob pattern stores entire aggregates as JSON strings. If injury representation changes from 7 boolean properties to a flags enum, the JsonConstructor must handle both old and new formats (or a migration must be planned).
- **Leaking Inventory mutability:** Don't expose `List<InventoryItem>` as a public property. After making Inventory a sealed class, expose `IReadOnlyList<InventoryItem>` publicly.
- **Recursive Defend call:** The current `CalculateDamageAfterDefense` method calls `Defend()` recursively on critical hits. This is unbounded -- a critical on the recursive call causes another recursive call. This is listed as medium-severity item 13 in the audit. If included in scope, add a depth guard or restructure.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Injury penalties | Scattered switch blocks in Character.Challenge | Centralized methods on InjurySet value object | Single source of truth for all injury-based penalties |
| Armor damage reduction | Switch over ArmorTier subtypes in Character | Virtual/base method on ArmorTier hierarchy | ArmorTier already has DamageReduction property; just add RollDamageReduction method |
| Broken table resolution | Switch in Character.ReceiveDamage mapping BrokenOutcome to booleans | Method on InjurySet or dedicated BrokenResolver | Eliminates the 7-arm switch and boolean flag explosion |

**Key insight:** Most of the refactoring moves existing logic to where it naturally belongs rather than creating new abstractions. The ArmorTier hierarchy and BrokenOutcome hierarchy already exist -- they just need behavior moved onto them.

## Common Pitfalls

### Pitfall 1: Breaking JSON Serialization Round-Trips
**What goes wrong:** Changing property names, types, or removing properties from serialized entities causes existing persisted data to fail deserialization.
**Why it happens:** The project uses JSON blob persistence -- each aggregate is serialized as a single JSON string in SQLite. Any structural change to a serialized entity affects all stored data.
**How to avoid:**
- Run `JsonSerializationTests` and `CharacterRoundTripTests` after every structural change.
- When changing injury representation from booleans to InjurySet, ensure the JsonConstructor still accepts the old boolean parameters OR update the JSON format and accept that existing data needs migration.
- For this project (pre-release, no production data), it is acceptable to break the old format if the new format is tested.
**Warning signs:** Tests in `Persistence/` namespace failing.

### Pitfall 2: Inventory Record Shallow Copy Bugs
**What goes wrong:** The `record` keyword gives Inventory value-type equality semantics, but its `List<InventoryItem>` member is a mutable reference. Using `with` creates a new Inventory sharing the same list.
**Why it happens:** C# records do a memberwise shallow copy. `Inventory with { MaxCapacity = newCapacity }` in `Character.Improve()` creates a new Inventory object pointing to the same `List<InventoryItem>` reference.
**How to avoid:** Convert Inventory to a sealed class. Remove all `with` expression usage on Inventory. Mutate in place via methods.
**Warning signs:** Two Character references appearing to share inventory state; mutations to one Character's inventory affecting another's.

### Pitfall 3: Forgetting to Update CharacterPlugin After API Changes
**What goes wrong:** The Semantic layer (CharacterPlugin, CampaignPlugin, EncounterPlugin) directly accesses domain properties and methods. Refactoring the domain without updating plugins causes compile errors or, worse, bypasses new invariants.
**Why it happens:** The Semantic layer is in a separate project (WretchedWhispers.Semantic) that references Core.
**How to avoid:** After every domain change, grep for usages in the Semantic project. The CharacterPlugin.CreateCharacterDto method (lines 263-315) reads nearly every property from Character -- any rename or type change must be reflected there.
**Warning signs:** Compile errors in WretchedWhispers.Semantic after Core changes.

### Pitfall 4: Breaking the Public API Surface
**What goes wrong:** User decision explicitly locks the public API surface. Changing method signatures on Character causes downstream breakage in services and plugins.
**Why it happens:** Overzealous refactoring that changes external contracts.
**How to avoid:** List all public methods on Character before starting. After refactoring, verify the same methods exist with the same signatures. New methods can be added (e.g., AddItem, RemoveItem delegates) but existing ones must not change.
**Warning signs:** Method signature changes in Character.cs, compile errors in tests or Semantic layer.

### Pitfall 5: Unbounded Recursion in Defend
**What goes wrong:** `CalculateDamageAfterDefense` calls `Defend()` recursively when `outcome.IsCritFree` is true (critical defence gives attacker a free attack). If the recursive Defend also rolls a critical, it recurses again without bound.
**Why it happens:** Natural 20 on defence (1/20 chance) triggers recursion. Unlikely but possible to stack.
**How to avoid:** If this medium-severity item is in scope, add a recursion depth parameter or extract the free-attack logic into a non-recursive path.
**Warning signs:** Stack overflow in combat-heavy test scenarios.

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| 7 boolean injury flags | Flags enum or value object | Current refactoring | Centralizes penalty logic, eliminates flag explosion |
| Record with mutable List | Sealed class with encapsulated collection | C# best practice | Prevents shallow copy bugs, enforces aggregate boundaries |
| Type-switching in consumer | Behavior on type hierarchy (strategy) | OOP fundamental | ArmorTier already has the hierarchy; just move behavior onto it |

**Deprecated/outdated:**
- Using `record` for entities with mutable collections is an anti-pattern in C# DDD. Records are for value objects with immutable state.

## Open Questions

1. **JSON Migration Strategy**
   - What we know: The project uses JSON blob persistence. Changing injury representation from 7 booleans to a flags enum changes the serialized format.
   - What's unclear: Whether existing persisted data matters (pre-release project) or if we can freely break the old format.
   - Recommendation: Since this is pre-release with no production data, freely adopt the new format and update all serialization tests. If backward compatibility is needed, add a custom JsonConverter that reads both old boolean format and new enum format.

2. **Scope of Medium-Severity Items**
   - What we know: User gave Claude discretion on whether to include medium-severity items (items 8-13).
   - What's unclear: How much time budget is allocated to this phase.
   - Recommendation: Include items that are touched by adjacent changes (e.g., fix unbounded recursion in Defend while refactoring combat logic) but defer purely additive items (Adversary enrichment, Omens implementation) per user's deferred list.

3. **Abilities Mutability**
   - What we know: Abilities is a sealed class with `ModifyAbility` that mutates in place (changing private setters). This was called out as item 7 ("mutable pretending to be a value object").
   - What's unclear: Whether Abilities should become truly immutable (returning new instances) or stay mutable.
   - Recommendation: Make Abilities return new instances from ModifyAbility (like HitPoints.Damage returns a new HitPoints). Update Character.Improve and Character.Degrade accordingly. This is a small change with clear semantics.
